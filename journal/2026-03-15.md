# Experiment Results Summary — March 14, 2026

All experiments: 200 generated tokens, 3 iterations per experiment, page cache dropped before each run.

## Setup

- **Machine:** 30 GiB RAM, 16 cores, CPU-only
- **Small model:** gpt-oss-20b-F16 (13 GiB, 24 layers, 32 experts, 4 used/token)
- **Large model:** gpt-oss-120b-F16 (61 GiB, 36 layers, 128 experts, 4 used/token)
- **Pressure:** memory locked by mlock_tool to reduce available RAM (0 = no pressure)

## Table Columns Explained

Each row is one experiment configuration. All times are averages across 3 runs in milliseconds.

| Column | What it measures |
|--------|-----------------|
| **Config** | Which optimizations are enabled (see below) |
| **Pressure** | How much RAM is locked away by mlock_tool (0 = full 30 GiB available) |
| **metadata** | Time to parse GGUF file header, architecture, vocabulary (~225ms, constant) |
| **mmap** | Time for mmap syscall. With prefetch ON: reads entire model from disk (MAP_POPULATE). With prefetch OFF: instant (lazy, no I/O) |
| **pin** | Time to mlock() compute weights into RAM (only with pinning ON, ~900ms small / ~1100ms large) |
| **context** | Time to allocate KV cache + compute buffers (~850ms small / ~1300ms large) |
| **warmup** | Time for dummy forward pass that pre-faults all weight pages (only with warmup ON) |
| **prompt_eval** | Time to process all input tokens in one batch. Includes page fault I/O if weights not yet in RAM |
| **generation** | Time to generate all ~199 output tokens, one at a time. Includes page fault I/O during generation |
| **wall** | Total wall-clock time from start to finish (sum of all phases above) |
| **faults** | Total major page faults (each = one 4KB page read from disk) |
| **tok/s** | Inference speed = eval_tokens / generation_time. Higher is better. Excludes all loading overhead |
| **tokens** | Number of tokens actually generated (should be 199; less means model hit EOS early) |

## Longer Output: 2000 generated tokens (March 15, 2026)

Small model only, lazy vs lazy_pinned, 10 iterations, `--seed 42` for reproducibility, essay prompt.

Purpose: test whether pinning's benefit accumulates over longer generation (10x more tokens than the 200-token experiments above).

**Pressure note:** 24 GiB pressure means 30 - 24 = 6 GiB free RAM. After KV cache (3 GiB) + compute buffers (0.4 GiB) + OS (~1.5 GiB), only **~1 GiB remains for model weight pages** (expert weights, compute weights, embeddings). The 13 GiB model must be served almost entirely from disk via page faults.

**Large model not tested here** — would take 10+ hours per pressure level with 2000 tokens. See the 200-token tables above for large model results.

### Pinning effect summary (2000 tokens, 24 GiB pressure)

| Input tokens | Wall: lazy | Wall: pinned | **Savings** | Gen faults saved | tok/s gain |
|-------------|-----------|-------------|-------------|-----------------|------------|
| 12 | 390s | 359s | **-32s (-8.1%)** | -882k | 5.2 → 5.7 (+10%) |
| 270 | 418s | 381s | **-37s (-8.8%)** | -989k | 4.9 → 5.4 (+10%) |
| 1180 | 418s | 385s | **-32s (-7.8%)** | -877k | 5.1 → 5.6 (+10%) |

At 0 pressure: pinning has zero effect on generation speed (14.4 vs 14.4 tok/s). The kernel keeps compute weights in page cache naturally when RAM is plentiful.

At 24 GiB pressure (~1 GiB left for model weight pages): pinning gives a consistent **8-9% wall clock improvement** and **10% tok/s improvement** across all prompt lengths. The benefit is entirely in the generation phase — pinning prevents the kernel from evicting compute weights (2.3 GiB) when it needs to page in expert weights from disk. Without pinning, compute weights compete with expert weights for the same ~1 GiB of page cache, causing ~880k additional page faults over 2000 tokens.

### Out-of-box default vs optimized (2000 tokens, 24 GiB pressure, 12 input tokens)

How much total speedup do our optimizations bring compared to stock llama.cpp?

| Config | metadata | mmap | pin | context | warmup | prompt_eval | generation | **wall** | faults | tok/s | tokens |
|--------|----------|------|-----|---------|--------|-------------|------------|----------|--------|-------|--------|
| default (out-of-box) | 225 | 4971 | 0 | 1006 | 14651 | 4001 | 382857 | **407715** | 7514954 | 5.2 | 1999 |
| lazy (no prefetch, no warmup) | 226 | 1 | 0 | 878 | 0 | 3530 | 385456 | **390273** | 7343807 | 5.2 | 1999 |
| lazy_pinned (+ pin compute) | 226 | 1 | 885 | 852 | 0 | 2898 | 353244 | **358564** | 6451977 | 5.7 | 1999 |

| Comparison | Wall savings | tok/s | Where the savings come from |
|-----------|-------------|-------|----------------------------|
| default → lazy | **-17s (-4.3%)** | 5.2 → 5.2 | Eliminates 5s mmap (MAP_POPULATE) + 15s warmup. Generation speed unchanged |
| default → lazy_pinned | **-49s (-12.0%)** | 5.2 → 5.7 | Above + pinning saves 30s in generation (fewer page faults) |
| lazy → lazy_pinned | **-32s (-8.1%)** | 5.2 → 5.7 | Pure pinning benefit in generation phase |

**Bottom line:** Out-of-box llama.cpp takes **408 seconds**. With our optimizations (disable prefetch + disable warmup + pin compute weights): **359 seconds**. That's **49 seconds saved (12%)** and **10% faster token generation** (5.2 → 5.7 tok/s).
