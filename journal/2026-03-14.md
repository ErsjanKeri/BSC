# 14 March 2026 - Fixing the Timing System and Scaling Up Experiments

## Summary

Discovered that llama.cpp's timing metrics were fundamentally misleading for our use case. Built a completely independent phase timing system, audited the entire codebase for hidden timing interference, and set up 90 experiments across all meaningful variable combinations.

## The Core Problem

llama.cpp calls `llama_perf_context_reset()` (`completion.cpp:170`) right before inference starts. This reset overwrites `t_start_us` with the current time, erasing all pre-inference costs from the reported metrics:

- `load_time` (warmup OFF) = time from reset to first eval, NOT from model load start
- `load_time` (warmup ON) = time from model start to warmup end (different meaning!)
- MAP_POPULATE cost (24s for large model): completely hidden
- Memory pinning cost (~1.3s): completely hidden
- Context construction (~860ms): completely hidden

This means ALL our previous experiments (March 8-12) had load costs hidden. The "595ms faster with mlock" finding was a measurement artifact — mlock was ~1.1s slower total, but its cost was invisible.

Full audit of timing variable writes in `src/`:
- `t_start_us`: written in 4 places (model load, context init, perf_reset, 2 commented-out)
- `t_load_us`: written in 4 places (init, RAII destructor, context init, synchronize overwrite)
- `perf_reset()`: called exactly twice (after warmup in common.cpp:1305, before inference in completion.cpp:170)
- `has_evaluated_once`: set once, never reset by anything
- No hidden surprises found.

## What We Built

### Independent Phase Timing

Added a `phase_timestamps` struct to `llama_model` (llama-model.h) with absolute `ggml_time_us()` captures at 9 phase boundaries:

```
T0: model load start           (llama.cpp:792)
T1: metadata + vocab done       (llama.cpp:834)
T2: mmap done                   (llama-model.cpp:6800)
T3: tensor pointers done        (llama-model.cpp:6953)
T4: pinning done                (llama-model.cpp:6990)
T5: context ready               (common.cpp, after llama_init_from_model)
T6: warmup done                 (common.cpp, after warmup block)
T7: prompt eval done            (completion.cpp, after first prompt decode)
T8: generation done             (completion.cpp, after last token)
```

Each point also captures major page faults from `/proc/self/stat`.

Nothing in llama.cpp's own timing system can affect these — they are completely decoupled from `perf_reset()`, `synchronize()`, and `has_evaluated_once`.

### JSON Output

At end of each run, prints one structured line:
```
[bsc_phases_json] {"t0_abs_us": ..., "metadata_ms": ..., "mmap_ms": ..., ...}
```

Phase durations are computed as T(n+1) - T(n). Page fault deltas per phase.

### Sanity Verification

Phases sum to total (off by 0.01ms rounding). Cross-checked against llama.cpp's own metrics:
- Our `phase_prompt_eval_ms` = llama.cpp's `prompt_eval_time` + 120ms (the gap from T6 to compute_start, which includes chat template init, threadpool setup, tokenization)
- Our `phase_generation_ms` = llama.cpp's `eval_time` + 2ms (sampling overhead)
- Our `phase_total_wall_ms` = llama.cpp's `total_time` + 1220ms (everything the reset hides)
- Page faults sum correctly across phases

### MAP_POPULATE Verification (strace-confirmed)

Verified at syscall level that MAP_POPULATE is working:
- Prefetch ON: `mmap(..., MAP_SHARED|MAP_POPULATE, ...)` → mmap takes 4725ms for small model (reads 13 GiB from disk)
- Prefetch OFF: `mmap(..., MAP_SHARED, ...)` → mmap takes 1.3ms (lazy, no I/O)
- Each binary loads its own `libllama.so` from the correct directory (confirmed with strace)

## Understanding the Inference Pipeline

Documented the full pipeline in `docs/llama-cpp-timing-mechanism.md`. Key clarifications:

- **`embd`** is a list of token IDs (integer indices). Prompt phase: 12 indices. Generation: 1 index per step.
- **`llama_decode()`** does: embedding lookup → forward pass → store K/V → output logits (201,088 floats)
- **Prompt eval does NOT generate a token** — it produces logits. The sampler picks the first token from those logits (~microseconds).
- **Prompt/generation distinction in timing** is purely a batch size check (`n_queued_tokens == 1` vs `> 1` in `synchronize()`). Same function runs both.
- **For MoE**: `ggml_mul_mat_id` computes each (token, expert) pair independently — no grouping by expert within a batch. 12 prompt tokens = 48 expert weight loads per layer. 1 generation token = 4 loads per layer.
- **KV cache**: pre-allocated for full 131k context window but we only use ~212 positions. Small model: 3090 MiB (12 layers full attention + 12 layers sliding window at 768 positions). Large model: 4635 MiB.

## Experiment Setup

### Configurations (5 useful out of 8 possible)

| Config | Prefetch | Warmup | Pinning | Why useful |
|--------|----------|--------|---------|------------|
| default | ON | ON | OFF | Out-of-box baseline |
| prefetch_only | ON | OFF | OFF | Isolates MAP_POPULATE effect |
| warmup_only | OFF | ON | OFF | Isolates warmup effect |
| lazy | OFF | OFF | OFF | Fully lazy, cleanest |
| lazy_pinned | OFF | OFF | ON | Lazy + selective pinning |

Eliminated 3 combinations where warmup ON + pinning ON (redundant — warmup loads everything, pinning's pre-load benefit already covered) or prefetch ON + pinning ON (prefetch loaded everything already).

### Full Matrix

5 configs × 2 models (small 13GiB, large 61GiB) × 3 pressure levels (0, 20, 22 GiB) × 3 prompt lengths (12, 270, 1180 tokens) = **90 experiments × 3 iterations = 270 runs**

Prompt files: `prompts/prompt_short.txt` (12 tokens), `prompts/prompt_medium.txt` (270 tokens), `prompts/prompt_long.txt` (1180 tokens). Token counts verified against the model's tokenizer.

Memory constraints:
- Small model: KV 3GiB + compute 0.4GiB + OS 1.5GiB = ~5 GiB floor. Max safe pressure ~23 GiB.
- Large model: KV 4.6GiB + compute 0.4GiB + OS 1.5GiB = ~7 GiB floor. Max safe pressure ~20 GiB. 22 GiB may OOM.
