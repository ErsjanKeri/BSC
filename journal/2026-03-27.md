# 27 March 2026 — MADV_RANDOM Catastrophe & 10-Run Data Challenges March 24 Madvise Results

## Summary

Two major findings:

1. **MADV_RANDOM is catastrophically harmful** — disabling kernel readahead on the model mmap causes 35x more page faults and 5.6x slower inference. Each fault reads exactly 4KB instead of the kernel's default ~128KB readahead. Confirmed at both pressure levels.

2. **The March 24 madvise results were misleading.** With 10 properly isolated runs, `MADV_WILLNEED` prefetching at 22 GiB is actually **27% slower** than lazy baseline, not 40% faster. Only weight pinning is a consistent, robust optimization.

## MADV_RANDOM Experiment

Added `--madvise-random` flag — applies `posix_madvise(POSIX_MADV_RANDOM)` to the entire model mmap after loading. The hypothesis was that the kernel's default readahead wastes SSD bandwidth on sequential speculation when our expert access is scattered.

### Results

At 20 GiB pressure (10 runs completed):
- **1940s avg wall time** vs 403s lazy → **4.8x slower**
- **229M avg faults** vs 7.9M lazy → **29x more faults**
- Progressive degradation: 1943s (run 3) → 2182s (run 10)

At 22 GiB pressure: all 10 runs **timed out at 3600s** (1 hour). Could not complete 2000 tokens.

### Why It Failed

`MADV_RANDOM` sets the readahead window to zero for **every** page fault on the mapping — not just expert weights, but attention weights, output weights, embeddings, everything. The kernel's default readahead (~128KB = 32 pages) is actually beneficial because tensor data is contiguous in memory. Even "random" expert access reads through weight matrices sequentially within each slice.

The fault count math confirms: 7.9M faults × 32 (readahead factor) ≈ 253M, close to the observed 229M. We literally converted every readahead hit into a separate synchronous 4KB page fault.

### Lesson

The kernel's default readahead is a net positive for mmap'd model weights. The right approach is targeted prefetching (`MADV_WILLNEED` on specific expert slices) rather than globally disabling readahead.

## Critical: March 24 vs March 25 Comparison at 22 GiB

| Config | Mar 24 (3 runs) | Mar 25 (10 runs) | Mar 24 vs lazy | Mar 25 vs lazy |
|--------|----------------|-------------------|----------------|----------------|
| lazy | 1152s | 1111s | — | — |
| pinned | 684s | 824s | -40.6% | -25.8% |
| madvise | 689s | 1415s | -40.2% | **+27.4%** |
| madvise+pinned | 658s | 843s | -42.8% | -24.1% |

**The madvise results completely reversed.** March 24 showed -40% improvement; March 25 shows +27% degradation. Possible explanations:

1. **Insufficient isolation on March 24.** With only 3 runs and 5s cooldown, the page cache may not have been fully cold between runs. Madvise may have appeared faster because it was benefiting from warm cache state left by the previous run.

2. **Cache drop ineffectiveness.** The `echo 3 > /proc/sys/vm/drop_caches` may not evict mlocked pages or pages under active I/O. With 5s cooldown (March 24) vs 15s (March 25), there's less time for background writeback to complete.

3. **Progressive cache degradation.** The March 25 madvise data shows clear run-over-run degradation: wall time escalates from 1205s (run 1) → 1738s (run 10), faults from 24M → 33M. With only 3 runs, March 24 may have captured only the "good" early runs before degradation set in.

4. **Binary differences.** The March 25 binary was rebuilt with `--madvise-random` code compiled in (even if not activated). This should not matter, but it's a difference.

## What Is Robust

**Pinning (`--pin-compute-weights`) is the only optimization that consistently helps across:**
- Both pressure levels (20g: -8.3%, 22g: -25.8%)
- Both experiment batches (March 24: -40.6%, March 25: -25.8%)
- All run counts (3 runs, 10 runs)
- Low variance (CV 0.3% at 20g, 4.3% at 22g — same as baseline)

**Madvise (`--moe-prefetch`) is unreliable:**
- Consistently harmful at 20g (+4.9% both datasets)
- Contradictory at 22g (-40% March 24 vs +27% March 25)
- High variance (CV 13.8% at 22g, March 25)
- Progressive degradation across runs

### Validated Beliefs

1. **Pinning helps at both pressures** — consistent across both datasets, all run counts

5. **Higher pressure amplifies pinning benefit** — 8% at 20g vs 26% at 22g (more eviction pressure = more value from locking)

### Unresolved: Madvise at 22 GiB

March 24 showed madvise as -40% improvement; March 25 shows +27% degradation. Even comparing run 1 only (before fragmentation): March 25 run 1 madvise = 1205s vs lazy 1046s = **+15% harmful**. The March 24 madvise result (2 runs after outlier removal) is an anomaly that cannot be reproduced.

### Unresolved: Absolute Value Gap at 22 GiB

March 24 pinned run 1 (684s) vs March 25 pinned run 1 (741s) = 8% slower despite identical mlock (2329.3 MiB, 314 tensors). March 24 lazy (1149s) vs March 25 lazy (1046s) = 9% faster. The baseline and optimized configs moved in opposite directions. This is not explained by the fragmentation hypothesis (both are run 1) and remains unexplained.

## Revised Understanding

The thesis narrative should focus on:

1. **Weight pinning** as the proven, robust optimization. The mechanism is clear: mlocking attention+output weights (2.3 GiB) prevents their eviction, ensuring only expert weights compete for the remaining page cache.

2. **Madvise as an investigation** that revealed the interaction between prefetching and page cache pressure. The finding that prefetching can be counterproductive under memory pressure (by polluting the page cache with readahead pages that evict useful cached pages) is itself a valuable result.

3. **MADV_RANDOM as a negative result** demonstrating that the kernel's default readahead is well-suited for contiguous tensor access patterns, even when the inter-tensor access pattern is scattered.

## Run-Over-Run Degradation at 22 GiB: Memory Fragmentation Hypothesis

### Observation

All 22 GiB experiments show **monotonic run-over-run degradation** — each successive run is slower than the previous, even with cache drops and identical configuration. This does NOT happen at 20 GiB.

**Max RSS (from `/usr/bin/time`) for lazy baseline at 22 GiB:**

| Run | RSS (MB) | Cumulative Loss (MB) | Wall (s) | Gen Faults (M) |
|-----|----------|---------------------|----------|-----------------|
| 1 | 6913 | 0 | 1046 | 22.0 |
| 2 | 6890 | 23 | 1060 | 22.1 |
| 3 | 6865 | 48 | 1069 | 22.1 |
| 5 | 6816 | 97 | 1094 | 22.3 |
| 10 | 6693 | 220 | 1185 | 23.8 |

**At 20 GiB (stable):** RSS = 8629→8613 MB over 10 runs (flat, <0.2% variation).

The RSS shrinks by ~22 MB per run at 22 GiB. Over 10 runs that's 220 MB less available for page cache, directly causing more faults and longer runtimes.

### Cross-Experiment RSS Erosion

The erosion is cumulative **across** experiment sets too (all run under the same mlock_tool session):

| Experiment (run 1) | Time | RSS (MB) |
|---------------------|------|----------|
| 2_lazy_22g | 04:14 | 6913 |
| 3_pinned_22g | 07:17 | 6700 |
| 4_madvise_22g | 09:45 | 6527 |
| 5_madvise+pinned_22g | 13:37 | 6190 |

Total RSS loss from first to last experiment: **~723 MB over 9 hours**.

### What Was Ruled Out

- **mlock behavior**: Identical across all runs and both experiments. 314 tensors, 2329.3 MiB locked, 0 failed. Every single run, March 24 and March 25.
- **Buffer allocations**: Identical — KV cache 3072 MiB, compute 414 MiB, model mmap 13141 MiB.
- **Log/artifact accumulation**: Total results directory is 120 MB — too small to explain 720 MB RSS loss.
- **Tensor tracing**: `GGML_TENSOR_TRACE=OFF` in this build. No trace files written.
- **Python runner**: Creates new `subprocess.run()` per run, writes 24 KB log, no accumulation.
- **IOMonitor**: Resets `samples = []` on each `start()`. No cross-run accumulation.
- **SSD throughput**: Actually slightly *increases* over runs (3.52→3.70 GB/s). SSD is not degrading.

### Hypothesis: Kernel Slab Fragmentation (UNVERIFIED)

**Assumption**: At 22 GiB pressure (~4.6 GiB free for a 12.85 GiB model), each run triggers extreme page reclaim activity: ~22M major faults, ~80M minor faults, ~47M voluntary context switches. The kernel's memory reclaim path allocates internal tracking structures (reverse-mapping entries, LRU lists, radix tree nodes, page table entries) that fragment physical memory over time.

`echo 3 > /proc/sys/vm/drop_caches` frees page cache, dentry cache, and inode cache, but does NOT compact:
- Unreclaimable slab allocations (`SUnreclaim` in `/proc/meminfo`)
- Page table fragments from repeated mmap/munmap of 12.85 GiB
- Kernel memory allocator fragmentation (buddy system holes)

At 20 GiB pressure (~5.15 GiB free), there's enough breathing room that the kernel reclaim activity is much lower (~8M faults), so fragmentation doesn't accumulate meaningfully.

**This is an assumption.** Verifying would require monitoring `/proc/meminfo` (specifically `SUnreclaim`, `Slab`, `PageTables`, `KernelStack`) between runs, which we did not do.

### Would Restarting mlock_tool Fix It?

**Unknown.** Restarting mlock_tool would:
1. Free 22 GiB of locked anonymous pages
2. Allow the kernel to compact/defragment physical memory
3. Re-allocate a fresh 22 GiB block

This *might* reset fragmentation if the slab entries were associated with the mlock_tool's address space or with the now-freed page structures. But kernel slab caches are global — they may persist even after the owning process exits. The proper test: restart mlock_tool between each experiment set (lazy, pinned, madvise, madvise+pinned) and check if run-over-run degradation disappears.

### Impact on Data Interpretation

This degradation means:
1. **10-run averages are biased upward.** Later runs are systematically slower, inflating the mean.
2. **Run 1 values are the closest to "clean" state** and the fairest comparison across configs.
3. **March 24's 3-run data captured only early (favorable) runs**, which partly explains why March 24 optimized configs appeared faster.
4. **The fairest cross-experiment comparison is run 1 vs run 1:**

| Config | Mar25 Run 1 | Mar24 Run 1 | Delta |
|--------|-------------|-------------|-------|
| lazy | 1046s | 1149s | -9.0% |
| pinned | 741s | 684s | +8.3% |
| madvise | 1205s | 760s | +58.7% |
| madvise+pinned | 841s | 661s | +27.2% |

The lazy baselines differ by 9% (Mar25 faster), but all optimized configs differ by 8-59% (Mar25 slower). This is NOT explained by fragmentation (run 1 is clean in both). There is a genuine difference between the March 24 and March 25 binaries or system state that remains unexplained.

### Implications for Experiment Design

For future experiments:
- **Restart mlock_tool between experiment sets** (not between runs — that changes the semantics of "under continuous pressure")
- **Monitor `/proc/meminfo`** between runs to track slab/kernel memory growth
- **Consider using run 1 values** as the canonical measurement, or at minimum report both run-1 and mean
- **Add a meminfo snapshot** to `run_experiments.py` before each run

### Note on Background Processes

During all experiments, VS Code server + Claude Code were running, consuming ~1.5 GiB RSS. This reduces the effective available page cache from ~4.6 GiB to ~3.1 GiB at 22 GiB pressure. Whether this was identical during March 24 experiments is unknown.
