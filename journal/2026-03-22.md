# Experiment Results — March 22, 2026

Small model only, 5 iterations per experiment, page cache dropped before each run.

## Setup

- **Machine:** 30 GiB RAM, 16 cores, CPU-only
- **Model:** gpt-oss-20b-F16 (12.85 GiB, 24 layers, 32 experts, 4 used/token)
- **Swap:** OFF (`swapoff -a`) — previous experiments (March 14-15) had swap ON, which silently offloaded ~4 GiB of KV cache/buffers to disk, inflating results. See "Key Discoveries" below.
- **Seed:** `--seed 42` for reproducible output
- **Pressure:** memory locked by mlock_tool to reduce available RAM (0 = no pressure)

## Key Discoveries (March 17-20)

Before running these experiments, we identified three critical issues with previous data:

1. **Swap was silently ON** during March 14-15 experiments. Swap offloads ~4 GiB of KV cache and other allocations to disk, giving the model ~4 GiB more effective page cache. All previous pressure experiments were measuring a less severe regime than intended.

2. **KV cache wastes 3 GiB of RAM** at default context size (131072). For 200-2000 tokens, only ~48 MiB of KV cache is actually used. The unused portion sits in physical RAM, competing with model pages for cache space. Setting `-c 2048` eliminates this waste.

3. **Memory pinning** (`--pin-compute-weights`) effect depends on both swap state and context size. Previous 8-9% benefit with swap ON was partly a swap-dependent artifact. With swap OFF, pinning helps ~5% at 22 GiB pressure (verified with 5 iterations, non-overlapping ranges).

## Table Columns

Each row is one experiment. All times are averages across 5 runs in milliseconds.

| Column | What it measures |
|--------|-----------------|
| **Config** | Which optimizations are enabled (see below) |
| **Pressure** | How much RAM is locked away by mlock_tool (0 = full 30 GiB available) |
| **metadata** | Time to parse GGUF file header, architecture, vocabulary (~227ms, constant) |
| **mmap** | Time for mmap syscall. With prefetch ON: reads entire model (MAP_POPULATE). OFF: instant |
| **pin** | Time to mlock() compute weights (2329 MiB) into RAM. Only with pinning ON (~900ms) |
| **context** | Time to allocate KV cache + compute buffers. ~23ms with ctx=2048, ~880ms with ctx=131072 |
| **warmup** | Time for dummy forward pass pre-faulting weights. Only with warmup ON |
| **prompt_eval** | Time to process input tokens. Includes page fault I/O if weights not in RAM |
| **generation** | Time to generate output tokens. Includes page fault I/O during generation |
| **wall** | Total wall-clock time (sum of all phases) |
| **faults** | Total major page faults (each = one 4KB page read from disk) |
| **tok/s** | Inference speed = eval_tokens / generation_time. Excludes loading overhead |
| **tokens** | Tokens actually generated (should be 199 or 1999) |

## Conclusions and Next Steps

### Experimental Standard Going Forward

All future experiments will use:
- **22 GiB memory pressure** (swap OFF) — leaves 8 GiB free, model is 12.85 GiB, creating real paging pressure (~62% fits)
- **2000+ token generation** — shows steady-state behavior, pinning/optimization effects accumulate over long generation
- **Full context window** (ctx=131072) — this is the realistic deployment scenario. Users don't manually tune `-c`. The KV cache waste is a real problem that any optimization must account for
- **Swap OFF** — clean, reproducible measurement without hidden KV offloading
- **`--seed 42`** — deterministic output for reproducibility

### Why 22 GiB Pressure

At 22 GiB with full context (ctx=131k), the small model hits the critical regime:
- 8 GiB free RAM, but KV cache eats ~3 GiB → only ~4 GiB for model page cache
- Model is 12.85 GiB → only ~31% fits in cache
- This creates enough pressure to see clear differentiation between configs (default: 4.0 tok/s, lazy_pinned: 4.6 tok/s = 15% improvement)
- Not so extreme that inference becomes unusably slow

### Key Findings from This Experiment Set

**1. Pinning effect is real and consistent (swap OFF, full context, 22 GiB, 2000 tokens):**
- lazy: 4.0 tok/s, 11,048,568 faults
- lazy_pinned: 4.6 tok/s, 9,170,542 faults
- **15% faster, 17% fewer faults** — verified with 5 iterations, non-overlapping ranges

**2. Context size dramatically affects pressure sensitivity:**
- ctx=2048 at 22 GiB: 10.7 tok/s (model mostly fits, mild pressure)
- ctx=131k at 22 GiB: 4.0 tok/s (KV waste creates severe pressure)
- Same pressure, 2.7x performance difference from unused KV allocation

**3. Removing prefetch + warmup is always beneficial under pressure:**
- default → lazy at 22 GiB ctx=131k: 512s → 503s wall (lazy + pinned: 435s)
- The 4.8s MAP_POPULATE + 4.3s warmup are pure waste under pressure

**4. Swap acts as implicit KV cache offloading:**
- Swap ON at 24 GiB ≈ swap OFF at 20 GiB (same effective model page cache)
- Swap masks the KV waste problem — fixing ctx is the proper solution

### Next Implementation Steps

1. **`madvise(MADV_WILLNEED)` prefetching** — after MoE router selects experts, prefetch their weight pages before computation. SSD is at ~58% utilization (measured via blktrace); prefetching could push toward 80-90% by overlapping I/O with attention computation
2. **`mlock2(MLOCK_ONFAULT)` lazy pinning** — zero-overhead alternative to current mlock. Pages get pinned on first access instead of eagerly read upfront. Eliminates the ~900ms pinning cost
3. **blktrace analysis at 22 GiB** — measure SSD utilization, request size distribution, and I/O latency in the new standard configuration
