# 23 March 2026 — blktrace Overhead Under Memory Pressure

## Summary

Attempted to capture block-level I/O traces during inference at our standard config (22 GiB pressure, swap OFF, ctx=131k, small model). blktrace adds unacceptable overhead at this pressure level due to trace data write buffering consuming scarce page cache.

## What We Tried

Ran blktrace on `/dev/nvme1n1` (model disk), writing binary trace files to `/dev/nvme0n1` (separate disk), during 100-token generation at 22 GiB pressure:

| Metric | Without blktrace (Mar 21) | With blktrace | Overhead |
|--------|--------------------------|---------------|----------|
| Generation time | 499,269 ms (2000 tok) | 67,641 ms (100 tok) | — |
| ms/token | 250 | 683 | **2.7x** |
| Faults/token | 5,527 | 14,053 | **2.5x** |

The blktrace run was 2.7x slower and had 2.5x more page faults per token. A previous attempt with 2000 tokens was even worse — 3.2x slower, 2.8x more faults, and the blkparse CSV conversion was OOM-killed.

## Root Cause: Trace Write Buffering

The blktrace relay daemon writes binary event data to files on nvme0n1 during inference. For 100 tokens, this produced **1.4 GiB** of binary trace files (`trace.blktrace.0` through `.15`).

These writes go through the Linux page cache. At 22 GiB pressure with ctx=131k, only ~4.1 GiB of RAM is available for page cache (8 GiB free − 3 GiB KV cache − 0.4 GiB compute buffers − 0.5 GiB OS). The 1.4 GiB of dirty write pages consumed **34% of the available page cache**, directly evicting model weight pages.

This creates a feedback loop: fewer model pages cached → more page faults → more trace events → more write data → fewer model pages cached.

## December Approach: tmpfs

In December (`journal/2025-12-21.md`), blktrace output was written to a dedicated tmpfs (`mount -t tmpfs -o size=8G tmpfs /mnt/blktrace_tmpfs`). tmpfs uses RAM directly, and the `size=8G` is a limit, not a reservation — only data actually written consumes RAM.

However, this does not solve the fundamental problem: whether trace data goes through page cache (nvme0n1 file writes) or tmpfs, it still consumes ~1.4 GiB of RAM that competes with model pages. With swap OFF, tmpfs pages cannot be swapped out. The overhead would be similar.

In December, the trace was only ~150 MB (short runs, fewer faults) and pressure was lower, so tmpfs worked. At our current scale (1.4 GiB trace data, 4.1 GiB total cache), it's too much.

## Decision: Use iostat Instead

`iostat -x 1` reads `/proc/diskstats` once per second and outputs one line of text. Zero memory overhead, zero page cache impact. It provides:
- Read/write throughput (MB/s) per second
- I/O utilization percentage
- Average request size and queue depth

This gives us the throughput-over-time graph we need without interfering with inference. We lose per-request detail (individual request sizes, D→C latency), but gain clean, uncontaminated measurements.

## What blktrace Data IS Useful For

The blktrace data we collected, while contaminated for timing/throughput measurements, may still be useful for:
- **Request size distribution** — the proportions (% of 4KB, 16KB, 256KB requests) should be representative even if the total count is inflated
- **I/O pattern characterization** — sequential vs random access patterns, which sectors are accessed

These structural properties of the I/O pattern are determined by the MoE architecture, not by memory pressure level. However, any quantitative conclusions (throughput, latency, faults/token) from blktrace runs at this pressure level are unreliable.

## tmpfs Does Not Pre-Allocate — Verified

We considered using tmpfs as isolated storage for blktrace output, with the idea of precisely controlling memory pressure:
- Mount tmpfs with `size=10G`, lock 12 GiB with mlock_tool → simulate 22 GiB pressure
- blktrace writes to tmpfs instead of nvme0n1 → no page cache interference

This requires tmpfs to **immediately consume its full size in RAM** on mount (like mlock does). We tested:

```
grep MemAvailable /proc/meminfo    →  29,879,324 kB
sudo mount -t tmpfs -o size=2G tmpfs /tmp/test_tmpfs
grep MemAvailable /proc/meminfo    →  29,879,324 kB  (unchanged)
```

**tmpfs is lazy** — it only consumes RAM when data is actually written, not on mount. The `size=` parameter is a cap, not a reservation. There is no option to force pre-allocation.

This means we cannot use tmpfs to create precise, predetermined memory pressure. Any approach involving "reserve X GiB of tmpfs + lock Y GiB with mlock = X+Y total pressure" fails because the tmpfs portion only materializes as blktrace writes data, making the pressure unpredictable and variable during the experiment.

### Conclusion

Block-level I/O tracing (blktrace) is fundamentally incompatible with our high-pressure measurement regime (22 GiB, ~4 GiB page cache). The trace output — whether written through page cache to disk or stored in tmpfs — consumes RAM that directly competes with model weight caching. This is a measurement Heisenberg problem.

We will use **`iostat -x 1`** instead, which reads `/proc/diskstats` once per second with zero RAM overhead, zero page cache impact, and no interference with inference.
