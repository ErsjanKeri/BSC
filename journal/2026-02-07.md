## Part 1: Understanding mmap, MAP_POPULATE, and File Loading

### 1.1 Three Ways to Load a File Into Memory

**Normal read (malloc + read):**
- `malloc(file_size)` allocates heap memory
- `read(fd, buf, file_size)` copies file data into that heap
- **Two copies exist**: one in kernel page cache, one in your heap
- 13GB model = 13GB heap + 13GB page cache = 26GB RAM used

**mmap (what llama.cpp uses):**
- `mmap()` maps the kernel's page cache directly into your address space
- **One copy exists**: the page cache IS your memory
- 13GB model = 13GB total
- Bonus: kernel can evict and reload pages when RAM is tight (it knows the backing file)

**Direct I/O (O_DIRECT):**
- Reads file straight from SSD into your memory, bypasses page cache entirely
- **One copy**, but no caching — next run reads from SSD again
- llama.cpp supports this as an option (`--direct-io`)

### 1.2 How Plain mmap Works (No Flags)

```c
addr = mmap(NULL, file_size, PROT_READ, MAP_SHARED, fd, 0);
```

This returns **instantly**. No data is read from disk. The kernel reserves a range of virtual addresses and says: "whenever you touch any of these addresses, I'll fetch that 4KB page from the SSD on the spot."

From the code's perspective, `addr` looks like a giant array — `addr[0]`, `addr[1000000]`, etc. But behind the scenes:
- If that page is already in RAM: normal memory read, no delay
- If that page is NOT in RAM: **page fault** -> kernel reads 4KB from SSD -> code continues

You never call `read()`. You just access memory and the kernel handles I/O transparently.

### 1.3 What MAP_POPULATE Adds

`MAP_POPULATE` is a constant bit flag defined by the Linux kernel. When added to the mmap flags, the kernel — **during the mmap() call itself** — walks through the entire file and faults in every page before returning.

| | mmap returns when... | Data in RAM? |
|---|---|---|
| Without MAP_POPULATE | Instantly | No. Pages loaded on demand |
| With MAP_POPULATE | After ALL pages loaded from SSD | Yes. Everything in RAM |

MAP_POPULATE turns lazy mmap into something that **behaves like** `malloc` + `read` the whole file. The 9-second load time observed in htop was the kernel reading all 13GB before `mmap()` returned.

### 1.4 MAP_POPULATE When Model Exceeds RAM

With a 61GB file on a 30GB RAM machine and MAP_POPULATE:
1. Kernel starts loading pages into RAM
2. RAM fills at ~30GB
3. Kernel **evicts** earlier pages to make room for later ones
4. By the time it finishes, layer 0's pages are gone
5. Inference starts, accesses layer 0 -> **page fault again**
6. You paid the cost of loading everything AND still get page faults

**MAP_POPULATE is actively harmful when the model exceeds RAM.**

### 1.5 The Code Path: prefetch -> MAP_POPULATE

The `prefetch` boolean in llama.cpp directly controls MAP_POPULATE. The chain:

```
llama-model.cpp:6797    ml.init_mappings(true, ...)
                                         ^^^^
                                         hardcoded true
        |
        v
llama-model-loader.cpp:890    llama_mmap(file, prefetch ? -1 : 0, ...)
                                                true ? -1 : 0 = -1
                                                (as size_t: huge nonzero number)
        |
        v
llama-mmap.cpp:388    if (prefetch) { flags |= MAP_POPULATE; }
                      nonzero -> adds MAP_POPULATE to mmap flags

llama-mmap.cpp:390    addr = mmap(NULL, file->size(), PROT_READ, flags, fd, 0);
                      flags now = MAP_SHARED | MAP_POPULATE
```

`MAP_POPULATE` is not a variable — it's a constant. `prefetch` is the only variable. The `|=` operator adds the MAP_POPULATE bit to the flags.

Additionally, when prefetch is on, it also calls `posix_madvise(POSIX_MADV_WILLNEED)` (line 395-400), a second hint telling the kernel to load data eagerly.

To disable MAP_POPULATE, change the one hardcoded `true` to `false` at `llama-model.cpp:6797`. There is no CLI flag for this — only `--no-mmap` exists, which disables mmap entirely.

### 1.6 What --no-mmap Does (Different Thing)

`--no-mmap` disables `mmap()` entirely. Falls back to `malloc` + `read`. Three distinct configurations:

| Setting | mmap used? | How data loads |
|---|---|---|
| Default | yes | mmap + MAP_POPULATE (eager) |
| `--no-mmap` | **no** | malloc + read (copies into heap, 2x RAM) |
| Our modification | yes | mmap without MAP_POPULATE (lazy on-demand) |

### 1.7 What is mlock?

`mlock` is a Linux syscall: "do NOT evict these pages from RAM, ever." Normally the kernel can evict mmap'd pages when RAM is tight (and reload from the file later). `mlock` pins them permanently.

llama.cpp's `--mlock` flag: "force system to keep model in RAM rather than swapping or compressing." Obviously can't work if the model exceeds RAM.

### 1.8 macOS Note

`MAP_POPULATE` is Linux-only (`#ifdef __linux__`). On macOS, mmap is always lazy regardless of the prefetch parameter.

## Part 3: Sparse Access Pattern Analysis

### 3.1 Token Embeddings (GET_ROWS Operation)

**File**: `llama.cpp/src/llama-graph.cpp`
**Line**: 1219

```cpp
// GET_ROWS operation
cur = ggml_get_rows(ctx0, tok_embd, inp->tokens);
//                         ^^^^^^^^  ^^^^^^^^^^
//                         250MB     e.g., [42, 17, 99]
//                         tensor    only 3 rows needed!
```

**Implementation** (`ggml/src/ggml-cpu/ops.cpp`, line 4623):
```cpp
for (int64_t i = ir0; i < ir1; ++i) {
    const int64_t i01 = *(int32_t *) ((char *) src1->data + ...);

    // Access ONLY specific row
    dequantize_row_q(
        (const void *) ((char *) src0->data + i01*nb01 + ...),
        //              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
        //              Pointer arithmetic to specific row
        (float *) ((char *) dst->data + ...), nc);
}
```

**Key insight**: Code accesses `src0->data + i01*nb01` (specific row offset), not entire tensor.

**Theoretical analysis:**
- Container: 250MB (32K vocab × 2880 dims × 2 bytes)
- Actual access: ~10 tokens × 5760 bytes = 57KB per inference
- **Potential waste: 99.98%** (if MAP_POPULATE loads entire 250MB)

### 3.2 MoE Experts (MUL_MAT_ID Operation)

**File**: `llama.cpp/ggml/src/ggml-cpu/ggml-cpu.c`
**Line**: 1628

```cpp
// Select which expert to use
const char * src0_cur = (const char *) src0->data + cur_a * nb02;
//                                                   ^^^^^^^^^^^^
//                                                   expert_id * bytes_per_expert
```

**Model structure (GPT-OSS-20B):**
- 32 experts per layer × 24 layers
- Top-4 expert selection (router chooses 4 out of 32)
- Each expert tensor: 2880 × 2880 × 32 = 134MB

**Theoretical analysis:**
- Container: 134MB (all 32 experts)
- Actual access: 4 experts × 4.2MB = 16.8MB per token
- **Potential waste: 87.5%** per layer
- **Total across 24 layers: ~2.8GB unused** (if MAP_POPULATE loads all experts)

## Part 4: Open Questions (As of Feb 7)

These were open at time of writing. Answers added retrospectively from later experiments.

1. **Does MAP_POPULATE actually load unused data?**
   -> *Answered (March 8)*: Yes. MAP_POPULATE faults in ALL pages. Without it, only accessed pages are faulted during warmup.

2. **What takes 5+ seconds during "loading"?**
   -> *Answered (March 8)*: llama.cpp's "load time" includes a warmup forward pass that triggers page faults. Model loading itself is <500ms. See journal entry 2026-03-08.

3. **Page fault behavior:**
   -> *Answered (March 8)*: With MAP_POPULATE ON, page faults happen during mmap(). With MAP_POPULATE OFF, they happen during the warmup forward pass. Total time is similar — faults just move between steps.

4. **Performance impact:**
   -> *Answered (Feb results.md)*: MAP_POPULATE OFF gives 15% (small model) to 35% (large model) load time improvement with no inference speed penalty.

## Part 5: Hypothesis (Untested)

**If sparse access is real:**
- MAP_POPULATE loads entire 13GB model
- But only ~4GB actually accessed (dense layers + 4-of-32 experts + few embedding rows)
- Disabling MAP_POPULATE could reduce loading overhead
- **But:** Pages might get faulted in anyway on first access

**Trade-offs to investigate:**
- Faster load time (avoid bulk page faulting)
- vs. Potential inference slowdown (page faults during generation)
- vs. Memory pressure (if model exceeds RAM)

**Expected outcomes:**
1. **Model fits in RAM**: Minor improvement (avoid upfront bulk fault-in)
2. **Model exceeds RAM**: Major improvement (avoid thrashing from trying to load 61GB into 30GB)
