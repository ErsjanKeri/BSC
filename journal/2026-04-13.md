# 13 April 2026 — Infrastructure Day: I/O-Compute Overlap, Cache Simulator, and LFU-Aging Tuning

## Summary

Three independent pieces of work that each pay off in the April 14 benchmark:

1. **`--uring-overlap` flag**: splits the per-layer io_uring load into two phases so the down-projection reads overlap with the up+gate matmul compute. Correctness verified bit-exact against the non-overlap path.

2. **Bit-exact cache policy simulator**: replays a ground-truth access sequence dumped from the C code (via `BSC_CACHE_DUMP`) against multiple policies. LRU, LFU, and LFU-aging all match their C implementations exactly (2377/2377 loads per run). Enables fast offline exploration of cache policy design space.

3. **LFU-aging tuning**: using the verified simulator we discovered that changing `aging_period` from `10 × cache_slots` to `3 × cache_slots` improves hit rate by 3–6 percentage points with zero implementation cost — beating or tying ARC at every cache size. Added `--uring-aging-mult N` CLI flag.

Supporting work: `--trace-mode {off,experts,all}` flag for efficient tracing (experts-only reduces trace file from ~1.7 GB to ~295 MB per 2000-token run), and fixed a bug where prompt tokens all had `token_id=0` in the tensor trace.

## 1. I/O-Compute Overlap: `--uring-overlap`

### Motivation

The per-layer io_uring load is 12 slots (3 projections × 4 experts). The current code loads all 12 synchronously, waits, then the CPU runs `mul_mat_id` for up, gate, swiglu, and down. But **up and gate are independent of the down weights** — down is only needed after swiglu produces its activation. So the down reads can overlap with up+gate+swiglu compute.

### Design

Split `llama_uring_expert_buf_load()` into three functions:

```c
phase1_load(layer, expert_ids)    // loads gate + up (8 slots), submits + waits, bumps epoch
phase2_submit(layer, expert_ids)  // submits down reads (4 slots), async — NO wait, same epoch
phase2_wait()                     // drains the pending down completions
```

In the graph, insert an extra callback node (`ggml_map_custom2`) between swiglu and `mul_mat_id(down)` that waits for phase2 and wires `compact_down->extra`. The `ggml_map_custom2` takes `act_result` as a dependency (ensuring it runs after swiglu) but passes `remapped_experts` through as its output (tiny tensor, no copy cost).

### Correctness question: can phase 2 evict phase 1's in-use slots?

This was the non-obvious part. Phase 1 has loaded up+gate and the CPU is reading them. If phase 2's eviction touched those slots while io_uring is writing down weights, the CPU would read corrupted data.

The fix: **phase 2 shares the same epoch as phase 1**. Specifically:
- Phase 1 bumps the epoch once, processes up+gate, marks 8 slots with the current epoch.
- Phase 2 does NOT bump the epoch. Its miss-evictions call `lfu_pick_victim()` which skips any slot with `epoch == current_epoch`.
- For LRU, the protection comes from geometry: phase 1's 8 slots sit at the MRU end of the LRU list, phase 2 only takes from the LRU back. Since `cache_slots ≥ 12` is enforced at init (`n_proj × n_expert_used`), the 4 phase-2 misses can never reach the MRU entries.

Both arguments are provable from the code, not assumed. The shared-epoch fix is a one-line change (don't bump in phase2_submit).

### Bug found during testing

The first test showed wrong output. Root cause: projection index ordering in the `.bscexp` pack file is **`0=down, 1=gate, 2=up`**, not the intuitive `0=up, 1=gate, 2=down`. My initial phase1 loaded projections `[0, n_proj-1)` expecting up+gate, but actually loaded down+gate. Phase2 loaded up instead of down. Fix: phase1 = `[1, n_proj)`, phase2 = `[0, 1)`. After the fix, output is bit-exact identical to the non-overlap path (MD5 verified at 200 tokens).

### Measured impact

At 100 tokens with c200 LFU (high miss rate), `uring_load_ms` dropped from 17730 ms to 16622 ms (−6.2%). Full wall-clock comparison in the April 14 journal.

## 2. Cache Policy Simulator (Bit-Exact Against C Code)

### Motivation

We want to test multiple cache policies without running the full io_uring pipeline for each one. Actual 2000-token runs take ~4–7 minutes; a sweep of 6 policies × 6 cache sizes × 6 domains = 216 runs × 4 min = 14 hours. Offline simulation takes seconds.

The catch: the simulation must be trustworthy. If it disagrees with reality we can't use it for policy decisions.

### First attempt: simulator replayed tensor traces

Initial simulator reconstructed the access sequence from per-token JSON trace files and replayed it. Results:

| Config | Real miss % | Sim miss % | Delta |
|---|---|---|---|
| c200 LRU | 100.0% | 100.0% | 0.0 pp ✓ |
| c200 LFU | 74.3% | 94.2% | **+19.9 pp** ✗ |
| c500 LRU | 40.8% | 45.1% | +4.3 pp (OK) |
| c500 LFU | 47.9% | 71.5% | **+23.6 pp** ✗ |

LRU was accurate; LFU was 17–24 pp too pessimistic. Not usable as-is.

### Root cause: missing prompt pre-fill

The tensor trace captures MUL_MAT_ID operations run by the ggml CPU backend. But the io_uring cache only sees loads where `n_tokens == 1` (single-token decode path). During prompt eval with `n_tokens > 1`, the standard mmap path is used and the io_uring cache stays empty.

However, the real cache has **one extra load at the very start**: the prompt's last layer (layer 23) is processed with `n_tokens == 1` just before generation begins. That first load fills slots 0–11 with prompt expert data, shifting all subsequent slot assignments by 12. For LFU with slot-index tie-breaking in victim selection, this shift changes which slots become the "revolving door" vs which stay stable — completely altering the hit-rate trajectory.

In my simulation, the first load was token 0 layer 0 (slots 0–11 = layer 0 data). In the real system, the first load is the prompt's layer 23 (slots 0–11 = layer 23 data, slots 12–23 = token 0 layer 0). That single extra batch explains the 20 pp discrepancy.

### Fix: dump the ground-truth access sequence from the C code

Added `BSC_CACHE_DUMP` environment variable to `load_projections()`. When set, every load() call writes a CSV row:

```
load_id,layer,p_start,p_end,n_real,eid0,...,eid15,hits,misses
```

This captures the exact sequence the cache sees, in the exact order, including any prompt pre-fill loads and with expert IDs exactly as they enter the load() function. The simulator now reads this CSV directly and replays it against different policies.

### Validation

With the CSV-based input, **every load() call's hit/miss count matches the C code exactly**:

| Policy @ c200, 100 tokens | Real hits | Sim hits | Match |
|---|---|---|---|
| LRU | 0 | 0 | 2377/2377 loads ✓ |
| LFU | 6864 | 6864 | 2377/2377 loads ✓ |
| LFU-aging | 7312 | 7312 | 2377/2377 loads ✓ |

Zero mismatches. The simulator is now a bit-exact oracle for any policy we implement in it.

## 3. LFU-Aging Tuning: One Line, 3–6 pp Improvement

### Setup

Captured six 2000-token access dumps (essay prompt from the canonical April 9 benchmark plus our five domain prompts: code, math, creative, factual, mixed). Ran a parameter sweep on the verified simulator.

The LFU-aging policy has one tuning knob: `aging_period = aging_mult × cache_slots`. Every `aging_period` accesses, all slot_freq counters are halved (`>>= 1`). The current value is `aging_mult = 10`.

### Sweep at c250 across 6 domains (mean hit rate)

| aging_mult | Mean hit % |
|---|---|
| 1× | 0.0% (halves too often, counters never accumulate) |
| 2× | 34.7% |
| **3×** | **36.1%** |
| 5× | 35.9% |
| 10× (current) | 33.2% |
| 30× | 24.1% |
| 100× | 19.4% |
| no aging (pure LFU) | 18.0% |

The optimum is at 3×. Going tighter (2×) hurts because counters don't differentiate; going looser (10×, 30×) lets stale popularity lock old experts. Our default of 10× was reasonable but not optimal for this workload.

### Other tuning knobs explored (and rejected)

| Knob | Values tested | Best | vs current |
|---|---|---|---|
| decay shift (halve vs quarter) | `>>= 1, 2, 3` | `>>= 1` | = current |
| initial freq on miss | 0, 1, 2, 3, 5 | 1 | = current |
| tie-breaking (slot-index vs round-robin) | index, round_robin | index | = current |

Only `aging_mult` had room for improvement. The slot-index tie-breaking is counter-intuitively optimal for MoE: the "revolving door" at slots 0–11 creates a stable front region (slots 12+) that accumulates frequency uncorrupted by eviction. Round-robin tie-breaking destroys this stability and drops to 0% hit rate.

### Comparison with complex adaptive policies

We also simulated ARC (Adaptive Replacement Cache) and W-TinyLFU (Window-TinyLFU with Count-Min Sketch) — both state-of-the-art adaptive policies used in production caching systems:

| Cache | LRU | LFU | LFU-aging 10x | **LFU-aging 3x** | ARC | W-TinyLFU | Belady |
|---|---|---|---|---|---|---|---|
| c250 (tight) | 0.0% | ~15% | 33.2% | **36.1%** | 0.0% | 30.1% | 58.0% |
| c498 (moderate) | 55.8% | ~35% | 52.8% | **58.6%** | 57.3% | 57.3% | 78.7% |
| c740 (oversized) | 72.5% | ~50% | 67.6% | **73.7%** | 73.7% (tied) | 74.3% | 87.9% |

**Tuned LFU-aging matches or beats ARC at every cache size** while being a one-line config change on our existing implementation. 2Q (Two-Queue) was also simulated but thrashes to 0% — the admission filter is poison for MoE's scan-style per-layer access pattern.

### Decision

Add `--uring-aging-mult N` CLI flag (default 10 for backward compatibility, use 3 for tuned). No new policies implemented. Full benchmark validation in the April 14 entry.

## 4. Cross-Domain Expert Pattern Analysis

Before choosing a policy, we looked at what the access patterns actually are. Captured 2000-token traces across 6 prompt domains (essay, code, math, creative, factual, mixed). Findings:

**Reuse distance** (tokens between consecutive accesses to the same layer+expert):
- 43–50% of reuses happen at distance = 1 (same expert re-selected next token)
- 74–81% at distance ≤ 5
- Mean reuse distance: 4.9–7.3 tokens
- Very strong temporal locality — favors recency-aware policies

**Token-to-token overlap** (fraction of current token's experts also in previous token):
- Essay: 43.6%, Creative: 50.1%, Code: 43.6%, Math: 42.9%, Factual: 44.9%, Mixed: 42.7%
- Creative has stickiest experts; others are similar

**Expert popularity entropy per layer** (max 5.0 for uniform):
- Mean across domains: 3.80 (creative) to 4.52 (code) bits
- Some layers have dominant experts (layer 22 expert 31 picked in 96% of tokens in one domain)

**Cross-domain variance on LFU-aging hit rates at c250:**
- 10x: range 27.2% (math) to 41.8% (creative), 14.6 pp spread, CV ~17%
- 3x: range 32.6% (mixed) to 43.0% (creative), 10.4 pp spread, CV ~10%
- **Tuning both raises the mean AND narrows variance across domains** — the worst-case domain improves most (math: +6.3 pp).

This motivated the choice of LFU-aging (frequency-based to exploit popularity skew) with aging (to handle temporal shift as router selections evolve). Pure LRU thrashes below the working set (288 slots), pure LFU locks on stale popularity, LFU-aging splits the difference.

## 5. Supporting Infrastructure

### Trace mode flag

The existing tensor trace captures every GGML op (~95 operation types) for every forward pass, producing ~1.7 GB per 2000-token run. For cache policy analysis we only need the MoE ops. Added `--trace-mode {off,experts,all}`:
- `off`: no tracing (default for benchmarks)
- `experts`: only MUL_MAT_ID and ADD_ID with expert_ids present (~295 MB/run, 83% reduction)
- `all`: original behavior

Enables 5-domain trace collection in ~15 minutes total instead of several hours.

### Prompt token_id bug fix

In `completion.cpp`, the phase tracking logic had:
```cpp
if (n_consumed < (int) embd_inp.size()) {
    tensor_trace_set_token_id(0);  // BUG: all prompt tokens get id 0
}
```

Changed to `tensor_trace_set_token_id(n_consumed)` so prompt tokens get distinct IDs. This doesn't affect the io_uring cache dumps (those use the C code's own `dump_load_id` counter) but cleans up the tensor trace outputs for offline analysis.
