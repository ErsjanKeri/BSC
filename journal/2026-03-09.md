# 9 March 2026 - Warmup Disabled: Confirming the Hypothesis

## Summary

Disabled the warmup forward pass alongside MAP_POPULATE and re-ran all experiments. The warmup was the dominant cost in "load time." Results confirm: for models exceeding RAM, warmup is actively harmful. Full data in [results-march.md](../time-tracking/results-march.md).

## What We Did

Added a third configuration to the existing experiment matrix:

| Config | MAP_POPULATE | Warmup | CLI |
|--------|-------------|--------|-----|
| Vanilla | ON | ON | (default) |
| Prefetch OFF | OFF | ON | (source change) |
| **Prefetch OFF + No Warmup** | **OFF** | **OFF** | **(source change + `--no-warmup`)** |

No recompilation needed for `--no-warmup` — it's an existing CLI flag (`common/arg.cpp:1394`). Used the `build_prefetch_off` binary with `--no-warmup` added to the command.

Same experiment conditions: 200 tokens, 10 runs, page cache dropped before each run, 5s cooldown.

## Results

### Small Model (20B, 13GB — fits in 30GB RAM)

| Config | Load | Inference | Total |
|--------|------|-----------|-------|
| Vanilla | 6.1s | 13.4s | **19.5s** |
| Prefetch OFF | 5.2s | 13.7s | **18.9s** |
| Prefetch OFF + No Warmup | 2.3s | 16.6s | **18.9s** |

End-to-end is the same (~18.9s) with or without warmup. Page faults move from load to inference but the total cost is identical — the entire 13GB model ends up in RAM either way.

### Large Model (120B, 61GB — exceeds 30GB RAM)

| Config | Load | Inference | Total |
|--------|------|-----------|-------|
| Vanilla | 65.4s | 36.6s | **101.9s** |
| Prefetch OFF | 40.0s | 36.7s | **76.7s** |
| Prefetch OFF + No Warmup | 4.3s | 37.2s | **41.5s** |

Total drops from **102s to 42s** (59% faster). Load collapses from 65s to 4s. Inference stays ~37s. Token generation speed identical across all configs (~6.1 tok/s).

## The 2.3s Load Time Makes Sense

Re-ran the March 8 timing decomposition on this Linux server (same `std::chrono` instrumentation, prefetch OFF, no warmup, small model). Results with warm page cache (best-case baseline):

| Step | Time (Small, 13GB) | Time (Large, 61GB) |
|------|-------------------|-------------------|
| GGUF header parse | 74.0ms | 65.9ms |
| Architecture + hyperparams + vocab | 162.8ms | 159.3ms |
| mmap (no MAP_POPULATE) | 0.0ms | 0.0ms |
| Backend buffer setup | 0.3ms | 0.5ms |
| load_all_data (pointer assignment) | 0.4ms | 0.6ms |
| **Model load total** | **238.8ms** | **228.3ms** |
| Context creation (KV cache + graph) | 861.0ms | 1298.6ms |
| **Warmup** | **SKIPPED** | **SKIPPED** |
| **Total before inference** | **~1100ms** | **~1529ms** |

The warm-cache timing above measures pure CPU/setup cost with no I/O. Under experiment conditions (cold cache), the small model reports 2311ms load time. The difference (~1200ms) represents cold-cache page faults spread across the load process — GGUF parsing, context creation, and the first prompt eval all trigger page faults when weights aren't cached. Note: with warmup disabled, llama.cpp's `load_time` timer encompasses everything up to and including the first prompt eval (confirmed by `prompt_eval_time ≈ load_time`: 2310.5ms vs 2311.1ms in results-march.md). The key takeaway from March 8 still holds: actual model loading is ~240ms, context creation ~860-1300ms, and warmup was the bottleneck eating the remaining seconds.

## Why Does Warmup Take 38 Seconds for 2 Tokens?

### The sanity check that didn't add up

From our experiments, generating 200 tokens with the large model takes ~37s of inference. That's ~185ms per token. The warmup processes just 2 tokens (BOS + EOS). So warmup should take roughly 370ms of compute. But measured warmup time is **38,410ms** — over 100x longer than expected. Something is fundamentally different about the warmup forward pass.

### Discovery: warmup uses ALL experts

Found the answer in `llama-graph.cpp:629`:

```cpp
n_expert_used = cparams.warmup ? hparams.n_expert : hparams.n_expert_used
```

During warmup, `n_expert_used` is set to `hparams.n_expert` (total experts) instead of `hparams.n_expert_used` (experts per token). This is by design — the warmup deliberately activates every expert to pre-fault all weight pages into RAM.

The model parameters:

| Model | Total Experts (`n_expert`) | Used per Token (`n_expert_used`) | Warmup Uses |
|-------|---------------------------|--------------------------------|-------------|
| Small (20B, 13GB) | 32 | 4 | **32** (all) |
| Large (120B, 61GB) | 128 | 4 | **128** (all) |

During warmup, the large model computes with **128 experts per layer** instead of 4. That's 32x more MoE weight data accessed per forward pass. Since MoE weights are the bulk of the model, warmup effectively reads the entire 61GB from SSD — which cannot fit in 30GB RAM, causing massive page eviction and re-faulting.

### Validation: A/B test with one variable

To confirm this is the cause and not just a hypothesis, we changed a single line — forced warmup to use `hparams.n_expert_used` (4 experts) instead of `hparams.n_expert` (128 experts) — rebuilt, and measured. All three tests: large model, prefetch OFF, cold cache (page cache dropped before each run).

| Config | Load Time | Eval (1 token) | Major Page Faults |
|--------|-----------|---------------|------------------|
| Warmup, 128 experts (original) | 40,012ms | 676ms | **339,145** |
| Warmup, 4 experts (modified) | 3,175ms | 329ms | **46,816** |
| No warmup | 1,079ms | 1,079ms | **21,959** |

All times are llama.cpp's reported metrics. Major page fault counts measured via `/usr/bin/time -v`. In the no-warmup row, Load Time ≈ Eval (both 1,079ms) because llama.cpp's performance timer is only reset after warmup — without warmup, both metrics report the same time window (**not additive**).

**Major page faults are the hard evidence.** Each major page fault = one 4KB page read from SSD.

- 128-expert warmup: **339,145 page faults** = ~1.3GB of data faulted in (but model is 61GB — pages are being evicted and re-faulted as the forward pass moves through layers)
- 4-expert warmup: **46,816 page faults** = 7.2x fewer — proportional to the expert reduction
- No warmup: **21,959 page faults** = only what actual inference needs

Load time dropped from **40,012ms to 3,175ms** (92% reduction) by changing warmup from 128 experts to 4. One variable, one line of code, measured outcome.

### What this means

The warmup's all-expert behavior is the root cause of the load time problem for large MoE models. It's not just "the model is big" — it's that warmup deliberately accesses 32x more data than inference needs. On a model that exceeds RAM, this means:

1. Warmup reads ~61GB of weight data through page faults
2. Only 30GB fits in RAM, so pages get evicted as new ones load
3. Real inference then needs to re-fault in the pages it actually uses
4. Net result: the same data gets loaded from SSD twice

The 4-expert warmup is interesting — it pre-loads exactly the weights inference will need (same 4 experts the router would pick), resulting in fast eval (329ms vs 1,079ms without warmup) at a fraction of the cost (3.2s vs 40s).

## Key Insight

For the small model, warmup is neutral — you pay the same total cost either way. For the large model, warmup is destructive — it wastes I/O bandwidth loading pages that can't survive in RAM. The 35 seconds saved (76.7s → 41.5s) is pure waste eliminated.

Token generation speed is unaffected in both cases. Disabling warmup has no quality or throughput penalty.
