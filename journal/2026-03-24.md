# 24 March 2026 — MoE Expert Prefetch via madvise(MADV_WILLNEED)

## Summary

Implemented and benchmarked a new optimization: inserting a custom GGML graph node that prefetches MoE expert weights via `posix_madvise(MADV_WILLNEED)` after the router selects experts but before the weight matrix multiplications. At 22 GiB pressure the results are dramatic — madvise alone matches pinning's 40% speedup. Combined with pinning: 43% faster than lazy baseline. At 20 GiB pressure, madvise is counterproductive (+3.2% slower) due to cache thrashing from redundant readahead.

## Implementation

### The Prefetch Gap

The MoE code path in llama.cpp has a natural insertion point between expert selection and weight access:

1. **Router** (`llama-graph.cpp:1038`) — `ggml_argsort_top_k()` selects 4 expert IDs from 32
2. **GAP** — expert IDs are known, but weights haven't been touched yet
3. **Weight access** (`llama-graph.cpp:1094-1161`) — three `build_lora_mm_id()` calls for up, gate, down projections trigger page faults

We insert a custom graph node in the gap that reads the selected expert IDs and issues `MADV_WILLNEED` for all 12 weight slices (4 experts × 3 projections) before any computation begins. This gives the kernel a head start on I/O.

### Graph Node Design

Used GGML's existing `ggml_map_custom1` mechanism — no new op types needed. The node:
- Takes `selected_experts` tensor as input (I32, shape `[n_expert_used, n_tokens]`)
- Stores pointers to `up_exps`, `gate_exps`, `down_exps` weight tensors in userdata
- Only thread 0 issues madvise (no contention)
- Passes through `selected_experts` unchanged — zero impact on graph semantics
- Gated by `--moe-prefetch` runtime flag — node is only inserted when flag is set

### Files Modified

- `llama-graph.cpp` — prefetch callback + node insertion in `build_moe_ffn()`
- `llama-graph.h` — `moe_prefetch` flag in graph params
- `common/arg.cpp` — `--moe-prefetch` CLI argument
- `common/common.h` — `moe_prefetch` param field
- `llama-model.cpp` — pass flag through to graph builder

### Per-Token Prefetch Volume

Each expert slice is ~3.5 MB (e.g., up_exps: 4096 × 14336 × 2 bytes F16 / 32 experts). Per layer: 4 experts × 3 projections × 3.5 MB = ~42 MB. Per token: × 24 layers = ~1 GB of readahead requested. This is aggressive — and explains why it's harmful when the cache is already warm.

## Analysis

### Why madvise works at 22 GiB

At 22 GiB pressure, only ~4 GiB of page cache is available for model weights (8 GiB free − 3 GiB KV cache − 1 GiB buffers/OS). The model is 12.85 GiB, so only ~31% fits. Pages are constantly being evicted. Every expert weight access is a cache miss → synchronous page fault → CPU stalls waiting for SSD.

`MADV_WILLNEED` converts these synchronous faults into asynchronous kernel readahead. The kernel starts reading expert weight pages from SSD while the CPU is still computing the previous operation. By the time `mul_mat_id` actually accesses the weights, some or all pages are already in cache.

The fault reduction is dramatic: 23.3M → 14.4M (-38%). This means ~9M page faults that would have stalled the CPU were avoided by the readahead arriving in time.

### Why madvise hurts at 20 GiB

At 20 GiB pressure, ~10 GiB is available, so ~78% of the model fits in cache. The kernel's natural LRU policy already keeps hot pages resident. Our madvise node requests ~1 GB of readahead per token (42 MB/layer × 24 layers). Most of these pages are **already cached** — the readahead is redundant. Worse, the kernel's readahead implementation may evict other useful cached pages to make room, causing a net increase in faults (6.9M vs 6.5M, +5.4%).

This is a known property of `MADV_WILLNEED`: it's harmful when the working set fits in memory. The optimization is only beneficial in the **cache-miss regime** where pages would have been faulted in anyway.

### Madvise vs Pinning: Different Mechanisms

Pinning (mlock) and madvise achieve similar speedups at 22 GiB (-40.6% vs -40.2%) through completely different mechanisms:

- **Pinning** prevents eviction of attention + output weights (2.3 GiB locked). Reduces fault count by keeping compute-critical pages permanently resident. Works at all pressure levels because locked pages are never evicted.
- **Madvise** prefetches expert weights before access. Reduces effective fault latency by overlapping I/O with computation. Only works when there's a cache-miss regime to optimize.

Combined (madvise+pinned): -42.8%, slightly better than either alone. The marginal gain is small (~2-3 percentage points), suggesting they address overlapping bottlenecks.

### SSD Throughput

| Config | Duration (s) | Total Read (GiB) | Mean (MiB/s) | Utilization |
|--------|-------------|-------------------|--------------|-------------|
| lazy | 1150 | 3921 | 3498 | 50% |
| lazy_pinned | 685 | 2034 | 3050 | 44% |
| lazy_madvise | 761 | 2142 | 2890 | 41% |
| lazy_madvise_pinned | 662 | 1924 | 2989 | 43% |

All configs remain far below the 7 GiB/s SSD theoretical max. Faster configs show *lower* mean throughput because they do less total I/O (fewer re-reads of evicted pages), not because the SSD is slower. The fundamental bottleneck remains synchronous page fault servicing — each fault stalls a CPU thread while waiting for a single 4 KB page, preventing the SSD from being saturated with concurrent requests.

## Open Questions

1. **Madvise outlier at 22 GiB** — run 3 regressed to 1100s. Needs rerun to confirm the 2-run average is representative.

2. **Pressure-adaptive prefetching** — madvise hurts at 20g, helps at 22g. Could we detect at runtime whether we're in the cache-miss regime and enable/disable prefetching accordingly? e.g., monitor fault rate over a sliding window.

3. **Readahead granularity** — we currently prefetch all 12 slices per layer upfront. Would it be better to prefetch only the current layer's expert slices, reducing the readahead footprint? Or prefetch the next layer while computing the current one?

4. **io_uring async reads** — madvise relies on the kernel's readahead heuristics. Direct async I/O via `io_uring` would give us explicit control over what pages to read and when, potentially achieving higher SSD utilization.
