# 16 March 2026 — MoE Expert Computation: How It Actually Works in llama.cpp

## Summary

Traced the exact code path of MoE expert selection and computation in llama.cpp. Understanding this is critical for designing prefetch/async optimizations — you can't optimize what you don't understand precisely.

## The MoE Forward Pass Per Layer

Each of the 24 layers (small model) / 36 layers (large model) runs this sequence:

1. **Attention sublayer** — Q/K/V projections, attention computation, output projection. Uses compute weights (pinned by `--pin-compute-weights`). Stores new K/V vectors in KV cache.

2. **MoE sublayer** — router + expert MLPs. This is where the expert weight page faults happen.

### Step 1: Router Scoring

**File:** `src/llama-graph.cpp:963`

```cpp
logits = build_lora_mm(gate_inp, cur);  // [n_expert, n_tokens]
```

The router multiplies the hidden state `cur` (output of attention, shape `[n_embd, n_tokens]`) by the router weight matrix `gate_inp` (shape `[n_expert, n_embd]`). Result: one score per expert per token.

For our small model: `[32, 2880] × [2880, 1]` = 32 scores. Tiny computation (~microseconds). The router weight matrix is part of compute weights (pinned).

### Step 2: Expert Selection

**File:** `src/llama-graph.cpp:978, 1038`

```cpp
probs = ggml_soft_max(ctx0, logits);                                    // normalize to probabilities
selected_experts = ggml_argsort_top_k(ctx0, selection_probs, n_expert_used);  // pick top 4
weights = ggml_get_rows(ctx0, probs, selected_experts);                 // get their weights
```

After softmax, `argsort_top_k` returns the indices of the 4 highest-scoring experts. `weights` contains their probability values (used later to weight the expert outputs).

### Step 3: Expert MLP Computation

**File:** `src/llama-graph.cpp:1094-1161`

Three matrix multiplications against the selected experts:

```cpp
up   = build_lora_mm_id(up_exps,   cur, selected_experts);  // up-projection    [n_ff, n_expert_used, n_tokens]
gate = build_lora_mm_id(gate_exps, cur, selected_experts);   // gate-projection   [n_ff, n_expert_used, n_tokens]
// ... activation function (SiLU/SwigLU) ...
down = build_lora_mm_id(down_exps, cur, selected_experts);   // down-projection  [n_embd, n_expert_used, n_tokens]
```

Each `build_lora_mm_id` maps to `ggml_mul_mat_id` at the compute level. This is where expert weight pages are accessed and page faults occur.

### Step 4: Aggregation

**File:** `src/llama-graph.cpp:1169-1193`

Expert outputs are multiplied by their probability weights, then summed:

```cpp
experts = ggml_mul(ctx0, experts, weights);  // weight each expert's output
moe_out = cur_experts[0];
for (i = 1; i < n_expert_used; i++)
    moe_out = ggml_add(ctx0, moe_out, cur_experts[i]);  // sum all 4
```

## How `ggml_mul_mat_id` Accesses Expert Weights

**File:** `ggml/src/ggml-cpu/ggml-cpu.c:1508-1681`

This is the critical function. It receives:
- `src0` — ALL expert weight matrices stacked: shape `[n_embd, n_ff, n_expert]`. This is one big mmap'd region.
- `src1` — input hidden states
- `ids` — the selected expert indices from step 2

The function does two things:

**Phase A: Group tokens by expert** (line 1596-1611, single-threaded)

```cpp
for (iid1 = 0; iid1 < n_tokens; iid1++) {
    for (id = 0; id < n_expert_used; id++) {
        i02 = ids[iid1][id];  // which expert did this token select?
        matrix_row_counts[i02]++;  // count tokens per expert
        matrix_rows[i02][count] = {id, iid1};  // record mapping
    }
}
```

During generation (1 token, 4 experts): `matrix_row_counts` has 4 non-zero entries, each with value 1.

During prompt eval (12 tokens, 4 experts each): `matrix_row_counts` has ~30-35 non-zero entries (some experts selected by multiple tokens), with varying counts. This enables batched matrix multiplication per expert.

**Phase B: Process each expert** (line 1621-1680, multi-threaded)

```cpp
for (cur_a = 0; cur_a < n_as; cur_a++) {       // loop ALL experts (32 or 128)
    if (matrix_row_counts[cur_a] == 0) continue; // skip unused

    src0_cur = src0->data + cur_a * nb02;        // pointer to expert's weights
    // ^^^ THIS IS WHERE PAGE FAULTS HAPPEN ^^^

    // matrix multiply: expert_weights × tokens_that_selected_this_expert
    ggml_compute_forward_mul_mat_id_one_chunk(..., src0_cur, ...);
}
```

The page fault happens at `src0_cur` — this points into the mmap'd model file. If those pages aren't in page cache, the CPU traps into the kernel, waits for disk I/O, then resumes. Each expert's weight region is ~14 MB (small model) spread across ~3,500 pages.

## The Page Fault Pattern During Generation

For each generated token, per layer:

```
1. Attention sublayer        — uses pinned compute weights, no faults
2. Router scoring            — uses pinned router weights, no faults
3. Expert selection          — just integer operations, no faults
4. ggml_mul_mat_id for up:
   - Access expert 3 weights → PAGE FAULT (CPU blocks ~50-100μs per page)
   - Multiply
   - Access expert 17 weights → PAGE FAULT
   - Multiply
   - Access expert 22 weights → PAGE FAULT
   - Multiply
   - Access expert 31 weights → PAGE FAULT
   - Multiply
5. ggml_mul_mat_id for gate:  — same 4 experts, BUT different weight matrices
   - Expert 3 gate weights → likely PAGE FAULT (different memory region)
   - ...
6. ggml_mul_mat_id for down:  — same 4 experts, third weight matrix
   - Expert 3 down weights → likely PAGE FAULT
   - ...
```

So per layer: up to 4 experts × 3 projections = 12 expert weight accesses, many causing page faults.

Per token: 12 × 24 layers = 288 expert weight accesses.

Measured: ~3,200 major page faults per token (from our 2000-token experiments: 6.4M faults / 2000 tokens). Each fault loads one 4KB page. So ~3,200 × 4KB = 12.5 MB read from disk per token.

## SSD Bandwidth Utilization

The SSD can do 7 GB/s. We're doing 12.5 MB per ~175ms per token = **0.07 GB/s = 1% utilization**.

Why so low? Page faults are **synchronous and serial**. The CPU can only fault on one page at a time per thread. Even with 8 threads, we get at most 8 concurrent 4KB reads — the SSD is barely working.

## Key Insight for Optimization

The router tells us which 4 experts we need BEFORE we access their weights. But the current code immediately accesses the weights (triggering blocking page faults) without any prefetching. The gap between "knowing which experts we need" and "accessing their weights" is where we could insert `madvise(MADV_WILLNEED)` or async I/O to start loading pages while the CPU does other work.

The challenge: in the ggml computation graph, the router node and the mul_mat_id node execute back-to-back. The only computation gap within a layer where we could hide I/O is during attention (before the router runs) — but we don't know the expert selection yet at that point.

Within `ggml_mul_mat_id` itself, we could prefetch all 4 experts at once before processing them serially, so experts 2-4 load while expert 1 computes.
