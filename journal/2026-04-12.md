# 12 April 2026 — Memory Budget Audit: Lazy Page Allocation Was Hiding 377 MiB of Compute Buffer

## Summary

We discovered that the compute buffer's 413 MiB allocation was not physically resident during our experiments — only ~36 MiB was actually committed to physical pages. This made our effective memory budget unpredictable: different prompts or batch sizes would commit different amounts of the compute buffer, silently changing how much memory remained for the expert cache. We fixed this by implementing `--eager-compute`, a flag that forces all compute buffer pages to be physically allocated at context creation via `memset`. This makes the memory budget fully deterministic and closes the long-standing mystery of why high cache-slot configurations (c290–c350) fit inside a 7G cgroup when our arithmetic said they shouldn't.

## How we discovered it

### The OOM mystery

We were investigating maximum viable io_uring cache sizes at each cgroup budget. Configurations c290, c310, c320, c340, and c350 all completed without OOM at 7G, which contradicted our budget arithmetic:

```
2350 (pin) + 3090 (KV) + 413 (compute) + 350×4.20 (cache) + 135 (misc) ≈ 7459 MiB > 7168 MiB (7G)
```

The 291 MiB overshoot should have caused OOM, but didn't.

### Instrumented binary on bsc/memory-debug branch

We added `bsc_print_rss()` instrumentation to `llama-model.cpp` and `llama-context.cpp` that reads `/proc/self/status` (VmRSS, VmLck, VmPin, RssAnon, RssFile) and the cgroup's `memory.current` at key lifecycle points: after load_tensors, after pin_compute_weights, after uring_expert_buf_init, after KV cache creation, after graph_reserve, and after decode iterations 1/2/5/50/150.

### Key finding 1: Pin charges correctly inside cgroups

Earlier (outside any cgroup) we observed pin adding +2350 MiB to VmRSS but only +5 MiB to cgroup `memory.current`. This was misleading — the model file was already in the system page cache from prior runs. When we ran inside a fresh cgroup after `drop_caches`, pin correctly charged +2349 MiB to the cgroup. VmLck confirmed: `2385364 kB = 2329 MiB` locked. Pin works as intended.

### Key finding 2: Both compute buffer and io_uring cache buffer are lazy-faulted

Both are allocated via `posix_memalign` → glibc → `mmap(MAP_ANONYMOUS)`. Physical pages are only created when something writes to a virtual address. Measurements inside a 7G cgroup at c350:

| Stage | VmSize (MiB) | cgroup (MiB) | Note |
|---|---|---|---|
| after graph_reserve | 18,400 | 5574.9 | compute: +496 MiB virtual, +0.0 MiB physical |
| after uring_buf_init (c350) | 19,900 | 5574.9 | cache: +1506 MiB virtual, +0.0 MiB physical |

Both buffers cost zero physical memory at allocation. Pages are committed only as io_uring writes to cache slots or as ggml's forward pass touches compute buffer regions.

### Key finding 3: Only 36 MiB of the 413 MiB compute buffer is physically used during decode

We tracked RssAnon through 150 decode iterations. It plateaued after iteration 2:

| Checkpoint | RssAnon (MiB) | Δ vs prev | What grew |
|---|---|---|---|
| pre-gen (KV done) | 3272.4 | — | baseline |
| decode iter 1 | 4512.1 | +1239.7 | 288 cache slots (1209) + ~30 MiB compute |
| decode iter 2 | 4778.9 | +266.8 | 62 more cache slots (260) + ~6 MiB compute |
| decode iter 5–150 | 4778.9 | 0.0 | stable — no further page faults |

Decomposition: `4778.9 − 3272.4 = 1506.5 MiB total growth`. Cache buffer: `350 × 4.203 = 1470.9 MiB`. Compute buffer resident: `1506.5 − 1470.9 = 35.6 MiB`.

**The compute buffer uses 8.6% of its allocation during decode.** The remaining 377 MiB is virtual address space that ggml never writes to because decode processes one token at a time (batch=1), while the buffer was sized for the worst-case prompt-eval batch (n_ubatch=512). Intermediate tensors like attention scores scale with batch size: `32 heads × 512 tokens × 512 × 2B = 16 MiB` at prompt eval vs `32 × 1 × 200 × 2B = 12 KiB` at decode.

### Key finding 4: All cache slots get physically written

We verified from existing run metrics that `cache_misses − cache_evictions == cache_slots` for every single configuration tested (c200 through c850). The cache buffer, unlike the compute buffer, does reach full physical occupancy during a 2000-token run.

### Why the arithmetic was wrong

The budget I had been computing assumed 413 MiB for the compute buffer. The actual cost was 36 MiB. The hidden 377 MiB was the "missing slack" that let c350 fit at 7G. In fact, with the real numbers:

```
2385 (pin) + 3164 (KV) + 108 (misc) + 1471 (cache c350) + 36 (compute) = 7164 MiB
```

That's 4 MiB under the 7168 MiB limit — fitting exactly, confirmed by `memory.peak = 7168` and `events.max ≈ 12,000` reclaim events in the cgroup stats.

## The fix: `--eager-compute`

### Problem

The 36 MiB figure is not a constant — it depends on prompt size, n_ubatch, and which code paths the forward pass exercises. A 5000-token prompt eval would commit substantially more of the 413 MiB buffer, permanently (anon pages, no swap). This makes the effective budget workload-dependent and undermines the reproducibility the cgroup methodology was supposed to guarantee.

### Solution

New CLI flag `--eager-compute` that `memset(0)`s the entire compute buffer immediately after `graph_reserve`. This forces all 413 MiB to be physically committed regardless of workload, making the non-reclaimable footprint deterministic.

Implementation spans 5 files:
- `ggml/include/ggml-alloc.h` / `ggml/src/ggml-alloc.c`: new `ggml_gallocr_clear_all()` iterates the graph allocator's vbuffers and clears each chunk
- `ggml/include/ggml-backend.h` / `ggml/src/ggml-backend.cpp`: new `ggml_backend_sched_clear_compute_buffers()` wraps the gallocr call
- `include/llama.h`: `eager_compute` field in `llama_context_params`
- `common/common.h` / `common/arg.cpp`: CLI flag + common_params plumbing
- `src/llama-context.cpp`: call after graph_reserve when flag is set

### Validation

Inside a 7G cgroup:

| Config | Without eager | With eager |
|---|---|---|
| Compute buffer RssAnon delta at alloc | +0 MiB | **+413.5 MiB** |
| cgroup after compute + KV + pin | 5575 MiB | **5989 MiB** |
| c350 @ 7G | Runs (4 MiB slack) | **OOM** (292 MiB over) |
| c260 @ 7G | Runs | **Runs** (58 MiB slack) |

## Corrected budget arithmetic

### Fixed costs (measured, deterministic with `--eager-compute`)

| Bucket | MiB | Source | Reclaimable? |
|---|---|---|---|
| Pin (mlocked file pages) | 2385 | VmLck = 2,385,364 kB | No (mlocked) |
| KV cache (ctx=131072) | 3164 | RssAnon delta after memset(0) | No (anon, swap=0) |
| Compute buffer (eager) | 413 | RssAnon delta after eager memset | No (anon, swap=0) |
| Misc anon (libs, stacks) | 108 | RssAnon at startup | No |
| **Total fixed** | **6070** | | |

### Variable cost: io_uring expert cache

Each cache slot = 4,406,784 bytes = 4.203 MiB (512-aligned from .bscexp pack header).

Non-pinned model file mmap pages faulted during forward passes (~28 MiB working set for embeddings, layer norms, biases) are reclaimable under pressure but temporarily occupy budget.

### Available budget for cache at each cgroup limit

```
available_for_cache = cgroup_limit − 6070 − 28 (mmap working set)
max_cache_slots = available_for_cache / 4.203
```

| cgroup memory.max | Available for cache (MiB) | Max cache slots | Practical ceiling |
|---|---|---|---|
| **7 GiB** (7168 MiB) | 1070 | 254.6 | **c250** (validated) |
| **9 GiB** (9216 MiB) | 3118 | 741.8 | **c740** (estimated) |
| **22 GiB** (22528 MiB) | 16430 | 3909 | Unconstrained |

### Impact on canonical April 9 results

All canonical winners fit under the eager ceilings:
- **c250 LFU @ 7G** (best at 7G): 250 < 254 — fits with ~17 MiB slack
- **c600 LRU @ 9G** (best at 9G): 600 < 741 — fits with ~593 MiB slack
- **Relative speedups are unchanged** because eager compute adds the same constant (377 MiB) to every configuration equally

### Updated experimental standard

The invocation template from April 9 gains one flag:

```bash
sudo systemd-run --scope --slice=bscexp.slice \
    -p MemoryMax=NG -p MemorySwapMax=0 -p MemoryAccounting=yes \
    /home/keri/llama.cpp/build/bin/llama-completion \
        -m <model> -p <prompt> -n 2000 -ngl 0 -no-cnv \
        --no-warmup --pin-compute-weights --eager-compute --seed 42
```

This ensures the compute buffer's 413 MiB is charged to the cgroup upfront, making the budget deterministic regardless of prompt size or n_ubatch.
