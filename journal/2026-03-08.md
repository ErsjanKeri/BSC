# 8 March 2026 - Load Time Decomposition: Where Do the Seconds Go?

## Summary

Investigated why llama.cpp reports ~5 seconds "load time" even with MAP_POPULATE off. Added timing instrumentation at every step of the loading pipeline. Found that **model loading itself takes <500ms** — the reported "load time" is dominated by a **warmup forward pass** (93% of total) that triggers lazy mmap page faults.

## Motivation

Our MAP_POPULATE experiments (results.md) showed:
- Prefetch ON: ~6100ms load time (small model)
- Prefetch OFF: ~5200ms load time (small model)

But with MAP_POPULATE off, `mmap()` returns instantly. So what's eating 5 seconds?

## Method: Timing Instrumentation

Added `std::chrono::high_resolution_clock` timestamps at every major step in the loading pipeline. Files modified (temporary, reverted after):

1. **`llama.cpp`** — around GGUF parse, load_arch/hparams/vocab, load_tensors
2. **`llama-model.cpp`** — around init_mappings, backend buffer setup, load_all_data
3. **`common.cpp`** — around model load, context creation, warmup

All timing printed via `fprintf(stderr, "[TIMING] ...")` to avoid log suppression.

Built with: `cmake .. -DCMAKE_BUILD_TYPE=Release && make llama-completion`

Ran locally: 13GB gpt-oss-20b-F16.gguf, 16GB RAM Mac M1 Pro, CPU-only (`-ngl 0`).

## The 8 Steps: Program Start to First Real Token

### Step 1: GGUF Header Parse (144ms)

`gguf_init_from_file()` in `llama-model-loader.cpp:522`.

Reads the file header: architecture name, hyperparameters, and a directory of all tensors (name, shape, type, byte offset). This is a small read (few MB) at the start of the 13GB file. After this, llama.cpp knows what's in the model but hasn't touched weight data.

### Step 2: Architecture + Hyperparams + Vocab (255ms)

`load_arch()`, `load_hparams()`, `load_vocab()` in `llama.cpp:800-816`.

Parses the metadata from Step 1 into C++ structs. Determines architecture (OpenAI MoE), reads n_layer=24, n_expert=32, n_embd=4096, etc. Loads 32K-token vocabulary with merge rules. All from parsed metadata — no weight data.

### Step 3: mmap (0.0ms)

`init_mappings()` in `llama-model.cpp:6798` -> `llama-mmap.cpp:390`.

The `mmap()` syscall. Creates a 13GB virtual address mapping. Without MAP_POPULATE, this is instant — the kernel just reserves address space. No data moves from SSD.

### Step 4: Backend Buffer Setup (0.4ms)

Lines 6803-6905 of `llama-model.cpp`.

Creates backend buffer objects — metadata telling ggml which memory region holds model weights. On CPU, this is just bookkeeping.

### Step 5: load_all_data (0.5ms)

`load_all_data()` in `llama-model-loader.cpp:947`.

For each tensor: computes `mmap_base + offset` and assigns that pointer to the tensor. Pure pointer arithmetic. No disk reads.

**Steps 1-5 total: ~470ms. This is actual model loading.**

### Step 6: Context Creation (753ms)

`llama_init_from_model()` in `llama-context.cpp:2420` -> constructor at line 21.

Three sub-steps:
- **Backend init**: Initialize CPU/GPU compute backends
- **KV cache allocation**: malloc memory for Key/Value cache across all 24 layers for the context window
- **Graph reserve**: Build dummy computation graphs (prompt-processing and token-generation sizes), run through scheduler to calculate required compute buffer sizes, allocate those buffers. No actual computation — just memory planning.

### Step 7: Warmup (23,043ms)

`common_init_from_params()` in `common.cpp:1274-1306`.

```cpp
if (params.warmup) {
    llama_set_warmup(lctx, true);
    tmp = {bos_token, eos_token};
    llama_decode(lctx, llama_batch_get_one(tmp.data(), tmp.size()));
    llama_memory_clear(llama_get_memory(lctx), true);
    llama_perf_context_reset(lctx);  // reset timers so warmup doesn't count in eval
    llama_set_warmup(lctx, false);
}
```

Runs a real forward pass with 2 dummy tokens (BOS + EOS), then throws away the result. This is where every model weight is accessed for the first time. With lazy mmap, each weight page triggers a page fault -> SSD read. On our 13GB model with 16GB RAM, this means faulting in most of the model from disk.

**This is NOT prefill.** Prefill processes the user's actual prompt. Warmup uses throwaway tokens and clears KV cache afterward.

The warmup exists to:
1. Fault in mmap pages (move weights from SSD to RAM)
2. Warm CPU caches
3. On Mac: let Metal compile GPU shaders
4. Ensure first real inference isn't penalized

### Step 8: Real Inference

Prompt tokenization, prefill of "Hello", then autoregressive generation. Weights already in RAM from warmup, so this runs at full speed.

## Key Finding

**llama.cpp's reported "load time" = Steps 1-7 combined**, measured as `ggml_time_us() - t_start_us` at first eval completion (llama-context.cpp:503). The warmup forward pass dominates.

This explains the MAP_POPULATE results:
- **MAP_POPULATE ON**: Page faults happen in Step 3 (mmap blocks). Warmup is fast (weights already in RAM).
- **MAP_POPULATE OFF**: Step 3 is instant. Page faults happen in Step 7 (warmup).
- **Total time is similar** — page faults just move between steps. The 15-35% savings with MAP_POPULATE OFF come from the kernel being smarter about on-demand paging than eager bulk loading.

## macOS Note

macOS does not support MAP_POPULATE (it's `#ifdef __linux__`). So on Mac, mmap is always lazy regardless of the prefetch parameter. The 23s warmup reflects faulting in most of the 13GB model into 16GB RAM under memory pressure.
