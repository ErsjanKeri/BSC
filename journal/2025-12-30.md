# December 30, 2025 - Motivation for Tensor-Level Tracing

## Key Realization

blktrace (block-level I/O tracing) has a **semantic gap**: it shows which disk sectors are read, but cannot tell us WHICH model components (layers, experts, tensors) are being accessed. 

From the Dec 22 experiments, we knew 1.67 GB got re-read under memory pressure — but couldn't identify whether it was embeddings, specific layers, or expert weights.

## Decision

Move from block-level tracing to **application-level tensor tracing** in llama.cpp. This became the primary approach (see tensor-tracing/).

## Why Application-Level is Better

| Aspect | blktrace (block-level) | Tensor tracing (app-level) |
|--------|----------------------|---------------------------|
| Granularity | Disk sectors | Named tensors |
| Semantic info | None | Layer, component, expert ID |
| MoE analysis | Cannot distinguish experts | Tracks which experts activated |
| Correlation | Sector → ??? | Tensor name → file offset → disk sector |

## What Was Speculated But Never Implemented

This journal entry originally contained ~1000 lines of speculative designs for:
- io_uring prefetching engine
- Pre-computed per-token access lists
- MoE expert-aware prefetching
- Hot tensor pinning with mlock()

None of these were implemented. The actual implementation focused on the tracing infrastructure itself (see tensor-tracing/ and journal entries from Jan 2026 onward).
