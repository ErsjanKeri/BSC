# January 2, 2026 - Tensor Tracer Design Decisions

## Decisions Made

### 1. Logging: mmap to tmpfs
- Write trace entries to `/dev/shm/tensor_trace.bin` (RAM-backed, no disk interference)
- Direct memcpy writes (~5-10 CPU cycles per entry)
- Copy to permanent storage after inference completes
- Later evolved: format went from 64 bytes → 128 → 256 → 1024 bytes per entry

### 2. Instrumentation: CPU backend hooks
- Location: `ggml/src/ggml-cpu/ggml-cpu.c`
- Method: `#ifdef GGML_TENSOR_TRACE` in each operation's compute_forward function
- Logs BEFORE the operation touches memory (captures the access, not just the computation)
- Scope: ALL operations (model params, intermediates, KV cache, embeddings)

### 3. Binary format (initial design, later revised)
Initial 64-byte struct with: timestamp_ns, token_id, layer_id, thread_id, operation_type, phase, tensor_ptr, file_offset, size_bytes, expert_id.

**Note:** This evolved significantly during implementation:
- 64 bytes proved too small (name truncation at 20 bytes)
- Expanded to 128 bytes, then 256, then 1024 bytes
- See journal entries 2026-01-07 and 2026-01-13 for the actual format used

### 4. CPU-only, all operations
- Hook the CPU backend specifically (not the dispatcher)
- Captures physical memory access, not just logical tensor access
- Enables correlation with blktrace (which tensor access caused which disk I/O)
- Thread-local buffers for concurrent writes (threads process different chunks of same tensor)

### 5. Token counter
- Tokens processed sequentially in autoregressive generation
- Global token counter incremented in llama_decode() (single-threaded context)
- No atomics needed for the counter itself
- Thread-local buffers still needed for concurrent log writes within a token

## What Was Discussed But Not Implemented

- alphaXiv-style 3D visualization (not needed, built WebUI + DesktopUI instead)
- Level 3 deep instrumentation inside inner loops (too much overhead)
- Detailed blktrace correlation pipeline (tensor tracing made this less important)
